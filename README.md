# Azure DevOps Self-Hosted Agent

A container image for running Azure DevOps self-hosted pipeline agents, built using the Wolfi-native supply-chain toolchain (melange + apko). A legacy Dockerfile build path is kept for reference but is not recommended for production use.

## How it's built — Wolfi, Chainguard, melange, apko

Traditional container builds use a Dockerfile: you start from a base image and layer commands that `curl` binaries, run `apt-get`, or call `pip install`. The result is an image whose contents are hard to audit — there is no signed manifest of what went in or why.

This project uses the [Chainguard](https://www.chainguard.dev/) supply-chain toolchain instead.

**[Wolfi](https://github.com/wolfi-dev/os)** is a minimal, musl-based Linux distribution maintained by Chainguard. Every package in the Wolfi repository is built from source with a signed SBOM and published with a cryptographically signed APK repository index. Because the index is signed, any APK you install from Wolfi can be traced back to its source and verified at install time — you are not trusting an opaque binary pulled from the internet.

**[melange](https://github.com/chainguard-dev/melange)** is a tool for building APK packages from a declarative YAML spec. For this project, `melange.yaml` defines all the tool binaries the agent needs (kubectl, kubelogin, Terraform, vendir, kluctl). melange downloads each binary, verifies it against a pinned SHA256 checksum, and packages everything into a signed `.apk` file. The signing key is generated fresh on each CI run — no long-lived build secrets. melange uses Linux user namespaces (via bubblewrap) to run builds in isolation without Docker-in-Docker.

**[apko](https://github.com/chainguard-dev/apko)** assembles a final OCI image directly from APK packages — no Dockerfile, no shell, no `RUN` layers. `apko.yaml` declares which packages go into the image (Wolfi base packages + the `azdo-agent-tools` APK built by melange), the user/group, the entrypoint, and environment variables. apko also generates an SPDX 2.3 SBOM automatically, giving a complete bill of materials for every image.

**The result:** every binary in the image is either a signed Wolfi APK or was SHA256-verified by melange before being packaged. The image has no package manager, no shell extras, and a complete SBOM. This is the same approach Chainguard uses for its own hardened images.

```
melange.yaml  →  melange build  →  azdo-agent-tools.apk  (signed)
                                           │
apko.yaml  ──────────────────────────────→  apko build  →  OCI image + SBOM
                  (Wolfi base packages) ──┘
```

## Quick Start

Download and run the latest pre-built image from GitHub Releases — no build required.

```bash
# Download the image tar from the latest release
gh release download --repo <your-org>/<your-repo> --pattern "azdo-agent-apko.tar"

# Load into Docker
docker load -i azdo-agent-apko.tar
# Output: Loaded image: azdo-agent:apko-amd64

# Run the agent
docker run --rm \
  -e AZP_URL=https://dev.azure.com/myorg \
  -e AZP_TOKEN=<your-pat> \
  -e AZP_POOL=MyPool \
  azdo-agent:apko-amd64
```

`AZP_TOKEN` must be a Personal Access Token with **Agent Pools (read & manage)** scope. The agent registers itself on startup and deregisters cleanly on `SIGTERM`/`SIGINT`.

## Build from Source

For enthusiasts who want to build the image locally from the melange + apko pipeline.

**Requirements:** Docker with privileged mode (melange uses bubblewrap for namespace isolation).

```bash
# Clone the repository
git clone https://github.com/<your-org>/<your-repo>.git
cd <your-repo>

# Build: generates a signing key if absent, then runs melange → index → apko
./build-apko.sh

# Load the image
docker load -i azdo-agent-apko.tar
# Output: Loaded image: azdo-agent:apko-amd64

# Verify all tools are present and working
docker run --rm --entrypoint /bin/bash azdo-agent:apko-amd64 -lc '
  kubectl version --client
  az version
  terraform version
  vendir --version
  kluctl version
  melange version
'

# Run the agent
docker run --rm \
  -e AZP_URL=https://dev.azure.com/myorg \
  -e AZP_TOKEN=<your-pat> \
  azdo-agent:apko-amd64
```

The build script pulls pinned Chainguard container images (`@sha256:` digests) for melange and apko — no external dependencies are resolved at build time beyond those digests.

**Build outputs:**

| File | Description |
|---|---|
| `azdo-agent-apko.tar` | OCI image tar (load with `docker load`) |
| `packages/x86_64/azdo-agent-tools-*.apk` | Signed APK package |
| `packages/x86_64/APKINDEX.tar.gz` | Signed APK repository index |
| `sbom-*.spdx.json` | SPDX 2.3 SBOM (generated by apko) |

## Build Approaches

### Primary: melange + apko (recommended)

The primary build uses [melange](https://github.com/chainguard-dev/melange) to produce a signed APK package containing all tools and the agent entrypoint, then [apko](https://github.com/chainguard-dev/apko) to assemble a minimal OCI image from Wolfi packages. No Dockerfile is involved at runtime.

**Benefits:**
- All binaries are SHA256-verified at build time (supply chain integrity)
- Image is assembled entirely from APK packages — reproducible and auditable
- SBOM generated automatically by apko (SPDX 2.3)
- Non-root by default (`agent` user, uid 1000)
- Multi-arch capable (amd64 + arm64; arm64 currently commented out in CI — see [CI notes](#cicd))

### Alternative: Dockerfile

> **Not recommended for production.** The Dockerfile does not verify SHA256 checksums for downloaded binaries (kubectl, kubelogin, terraform, vendir, kluctl), which is a supply chain risk compared to the melange path. It is kept as a reference and local development fallback only.

A `Dockerfile` based on `cgr.dev/chainguard/wolfi-base` installs the same toolchain via `curl` + `pip` at image build time.

## Toolchain

| Tool | Version | Checksum verified |
|---|---|---|
| kubectl | 1.35.2 | Yes (SHA256, both arches) |
| kubelogin | 0.2.16 | Yes (SHA256, both arches) |
| Terraform | 1.14.7 | Yes (SHA256, both arches) |
| vendir | 0.45.2 | Yes (SHA256, both arches) |
| kluctl | 2.27.0 | Yes (SHA256, both arches) |
| Azure CLI | ~2.84.0 | Yes — Wolfi `az` APK (`~=` fuzzy match picks up latest epoch), verified by signed Wolfi repository index |
| melange | 0.45.3-r1 | Yes — pinned Wolfi APK with signed repository |
| Python 3, git, jq, yq, make, openssh, curl | Wolfi latest | Via signed Wolfi APK repository |

> **Azure CLI** is installed as the Wolfi `az` APK rather than via `pip`. Package integrity is enforced by the signed Wolfi repository index (same supply chain assurance as all other Wolfi packages).

## Key Files

| File | Purpose |
|---|---|
| `melange.yaml` | APK build spec — declares version variables, downloads, SHA256-verifies, and installs all tool binaries |
| `apko.yaml` | Image assembly config — packages, users, entrypoint, environment variables |
| `build-apko.sh` | One-command local build wrapper (keygen → melange → index → apko) |
| `update-checksums.sh` | Refreshes SHA256 pairs in `melange.yaml` after a version bump (run before CI will pass) |
| `Dockerfile` | Wolfi-based Dockerfile build (reference/fallback only — no checksum verification) |
| `start.sh` | Azure DevOps agent entrypoint installed to `/azp/start.sh` in the image |
| `melange.rsa.pub` | Public signing key for local APK repository (committed) |
| `renovate.json` | Renovate config — custom regex managers for all tool versions |

## Local Build

Requires Docker with privileged mode support (melange uses bubblewrap namespaces).

```bash
# Full build: generates signing key if absent, builds package and image
./build-apko.sh

# Load the image
docker load -i azdo-agent-apko.tar

# Verify tools (amd64)
docker run --rm --entrypoint /bin/bash azdo-agent:apko-amd64 -lc '
  kubectl version --client
  az version
  terraform version
  vendir --version
  kluctl version
  melange version
'
```

> After `docker load`, the image tag includes the arch suffix: `azdo-agent:apko-amd64` (not `azdo-agent:apko`).

## CI/CD

GitHub Actions (`.github/workflows/build.yml`) runs on pushes and PRs to `main`:

- **Build with melange + apko** — installs melange via `chainguard-dev/actions/setup-melange` and apko from its GitHub release binary (`APKO_VERSION`), builds the amd64 package, assembles the image, loads it into Docker, and runs tool version checks.

> CI installs melange and apko as native binaries on the runner. The distroless apko container image has no shell and cannot run on GitHub Actions runners.

**arm64 and Dockerfile jobs** are currently commented out in the workflow. To re-enable, uncomment the relevant steps/jobs — the code is preserved in `build.yml`.

## Running the Agent

The agent is configured via environment variables at container start. `AZP_TOKEN` must be a Personal Access Token with **Agent Pools (read & manage)** scope.

| Variable | Required | Description |
|---|---|---|
| `AZP_URL` | Yes | Azure DevOps organization URL (e.g. `https://dev.azure.com/myorg`) |
| `AZP_TOKEN` | Yes | Personal Access Token with Agent Pools (read/manage) scope |
| `AZP_POOL` | No | Agent pool name (default: `Default`) |
| `AZP_AGENT_NAME` | No | Agent name (default: hostname) |
| `AZP_WORK` | No | Work directory (default: `_work`) |

```bash
docker run -e AZP_URL=https://dev.azure.com/myorg \
           -e AZP_TOKEN=<pat> \
           -e AZP_POOL=MyPool \
           azdo-agent:apko-amd64
```

The agent registers itself on startup and deregisters cleanly on `SIGTERM`/`SIGINT`.

> `TARGETARCH` is hardcoded to `linux-musl-x64` in the image environment. This tells the Azure Pipelines API which agent package to download at startup and should not be changed for amd64 Wolfi/musl images.

## Updating Tool Versions

[Renovate](https://docs.renovatebot.com/) automatically opens PRs when new versions are available for all tracked tools. Version variables are defined in three files that must stay in sync:

- `melange.yaml` — pipeline shell variables + SHA256 checksums (source of truth for the build)
- `apko.yaml` — `environment:` entries (runtime env vars baked into the image)
- `Dockerfile` — `ENV` declarations (fallback path only)

Renovate updates the version strings in all three files. **SHA256 checksums in `melange.yaml` are not updated automatically** — after a Renovate PR lands, run:

```bash
./update-checksums.sh
git add melange.yaml
git commit -m "chore: update checksums for <tool> <version>"
```

CI will fail on the Renovate PR until checksums are refreshed. This is expected — the SHA mismatch is the gate that ensures the new binary is verified before merging.

> Azure CLI checksums are not handled by `update-checksums.sh` (no machine-consumable SHA available from PyPI). Only the version string is updated by Renovate.

## Signing Key Management

The private key (`melange.rsa`) is gitignored and never committed. The public key (`melange.rsa.pub`) is committed and referenced by `apko.yaml`. CI generates a fresh ephemeral signing key per run.

```bash
# Regenerate keypair (if lost or rotating)
melange keygen

# Commit only the public key
git add melange.rsa.pub && git commit -m "chore: rotate melange signing key"
```

After rotating, all consumers of the local APK repository must re-import the new public key.

## Known Limitations

| Area | Limitation |
|---|---|
| Azure CLI epoch suffix | `az~=2.84.0` (fuzzy match) — APK `~=` selects the latest epoch of that upstream version automatically, so Wolfi security-patch epochs are picked up without a code change |
| Dockerfile | No binary checksum verification — not suitable for production |
| Wolfi base packages | `python3`, `git`, `jq` etc. pull the latest Wolfi version at build time — not pinned |
| arm64 CI | Disabled (commented out) — re-enable by uncommenting QEMU + arm64 steps in `build.yml` |
| Melange version | `melange=0.45.3-r1` (Wolfi APK epoch format) is not tracked by Renovate — bump manually |
| `chainguard-dev/actions/setup-melange` | Pinned to `@main` in CI — not a release tag, so not tracked by Renovate |
